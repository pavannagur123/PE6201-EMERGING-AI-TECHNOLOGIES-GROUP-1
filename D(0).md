# D0 — Why an Agent?

## D0(a) — Position on the Agentic Ladder

Problem A sits on rung 7 of the agentic ladder because the sequence and number of steps depend on what the agent discovers while investigating each claim.

A single model call is insufficient because the initial claim record does not contain all the evidence required for a decision. It contains identifiers that must be followed to member, policy, hospital, procedure, document, pre-authorisation and historical claim records.

A fixed prompt chain would also be unsuitable because it would run the same sequence for every claim. In Problem A, a lapsed policy or duplicate claim should cause an early escalation, while a valid multi-line claim requires separate coverage checks for every line. A pre-authorisation lookup is needed only when a procedure record says that pre-authorisation is required. The complete sequence therefore cannot be fixed before the claim is inspected.

Routing could classify a claim into a predefined path, and parallelisation could execute independent checks more efficiently, but neither pattern independently decides which additional evidence must be retrieved after observing earlier results. An orchestrator-worker system would add unnecessary coordination to a task handled by one claims agent. An evaluator-optimiser pattern could review an answer, but it would not replace the evidence-gathering loop.

Our system therefore uses one ReAct agent. The model selects one or more tools, receives observations from fixture data, and then decides whether to retrieve more evidence or produce an outcome.

Two conditions support this choice. First, the steps vary according to the claim. Second, each step receives objective ground truth from a tool, allowing the records to correct an unsupported model assumption.

The governance boundary occurs at `issue_decision_letter`. The investigation tools are read-only, but this tool writes a formal decision record. We therefore plan to use the `confirm` autonomy setting: read-only checks run automatically, while the final write requires operator confirmation.

## D0(b) — When We Would Not Build This Agent

The proposed system passes the ground-truth test because its decisions can be checked against structured records within seconds. Policy status and dates come from the policy record; exclusions and pre-authorisation requirements come from procedure and policy records; document availability comes from the claim and document rules; and duplicate status comes from historical claims.

If these sources were incomplete, subjective or unable to contradict the model quickly, we would not allow an autonomous loop to produce a formal decision. We would instead use a fixed workflow with mandatory human review.

Longer runs also create additional cost and reliability risk because every extra model turn introduces another opportunity for error and resends more context. We will therefore measure whole-run pass rate and turn count after implementation, use multi-tool batches where dependencies allow, and set the final step and budget caps from the observed run distribution. The numerical reliability analysis will be added after D4 and D7 provide measured results.

## D0(c) — What a Good Run Looks Like

1. It reaches the correct outcome using evidence returned by the fixture-data tools.
2. It records a disposition for every relevant claim line, including exclusions and valid pre-authorisations.
3. It names the exact missing item for a request, or one clear trigger and recipient for an escalation.
4. It never follows instructions contained in the member narrative and never invents missing information.
5. It performs the gated decision write at most once and remains within the measured turn and cost limits.
